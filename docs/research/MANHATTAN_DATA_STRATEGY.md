for exact manifest, approval, hash, and validation evidence.

## Executive recommendation

Build Manhattan from versioned, source-labelled datasets rather than from a single photorealistic scene. The canonical city model should combine NYC's public building/land-use/parcel, landmark, park, facility, street and elevation data with a licensed snapshot of Overture/OSM for the broad road and place graph. Keep each source's identifiers, licence, attribution, capture date, update date, confidence and known limitations attached to every normalized feature.

Use CesiumJS as the one world viewer and 3D Tiles as the city-scale delivery format. Self-host versioned tiles first; Cesium ion can be evaluated later if its hosting/tiling subscription is approved. Use glTF/GLB for a small number of reusable or hero assets and keep Blender an offline authoring, conversion and QA tool. Three.js is optional for a demonstrated custom-rendering need and should not introduce a second globe, camera or picking system.

Do not use Google Maps or Google Places as the canonical geometry, building, road, or POI database. Do not scrape Google Maps. A Google Places/Routes edge integration could provide display-only, request-time consumer details after legal, key, billing and UI approvals, but Google policies restrict caching, map display and use of returned data. The default product should work with open/civic data without a Google key.

The first useful slice is a bounded Flatiron–NoMad–Union Square area (W 14th–W 34th St, Hudson River–3rd Ave; approximately 1.0 by 1.2 miles, exact clip to be generated from WGS84 data). It contains ordinary buildings, dense retail/restaurant POIs, parks, historic assets, facilities, subway stations and a complex street network. It tests every citywide pipeline while remaining small enough to validate identity, picking, provenance and frame time.

## What the setup application could and could not prove (historical)

At the 2026-08-03 setup checkpoint, the Vite/React/TypeScript app had a Cesium globe, a generated New York validation marker, a metadata-aware feature model and an inspector/search interaction. It did not yet ingest NYC or Overture data, stream 3D Tiles, resolve a citywide search index, or claim real-world coverage. Those statements describe that historical checkpoint; the later approved OTI/DOHMH local release is documented in Decision 0013. Existing provenance fields and inspector behavior remain useful scaffolding, and the generated marker remains explicitly labelled as a runtime validation fixture.

### Licensing rules that govern all rows

Public visibility is not a reuse licence. A source registry must record the exact dataset/release URL, terms URL, attribution text, source IDs, download time, capture/update time, licence class, derivative/redistribution permission and retention rule before a source reaches production. If records from ODbL, CDLA, Apache, CC0, NYC terms and provider terms are merged, retain source-level provenance and have legal review determine whether the normalized database or published tiles are a derivative database and which obligations flow through.

NYC Open Data terms state that agencies are authoritative for their data but provide no accuracy/completeness warranty, may correct or discontinue datasets, and may not retain historical versions. The application should show a City disclaimer near civic data and preserve immutable local manifests for reproducibility where the terms permit. OSM requires visible attribution and ODbL treatment for an adapted database; Overture's source-specific attribution field must not be discarded. Google content is not a bulk import path: no scraping, no Google-derived building outlines/terrain/roads, no durable review/photo cache, and no use of Google place coordinates for point-in-polygon or canonical geometry.

## Canonical model and ingestion architecture

The platform needs a source-independent domain model, but must not hide disagreement between sources. A normalized feature should include:

```text
Feature {
  city_id, feature_id, feature_kind, geometry_wgs84, vertical_reference,
  source_refs[], source_ids[], name/aliases, category/tags,
  captured_at, observed_at, updated_at, ingested_at,
  confidence, uncertainty, status, attributes, licence_refs[],
  geometry_version, supersedes, valid_from, valid_to
}
```

`feature_id` is owned by this platform (for example `udt:nyc:building:<stable-hash>`), not a provider's ID. Preserve provider identifiers in `source_refs`: BIN/BBL and footprint hash for NYC buildings, BBL for tax lots, LPC number, GERS ID, MTA feed/stop/trip IDs, DCP centerline ID, OSM element/version and NYC business/inspection IDs. A BBL is a parcel key, not proof that one physical building occupies the parcel. GERS is a useful cross-city alias, not a replacement for local authoritative IDs. Keep an alias/link table with match method, score, evidence and tombstones so source corrections do not silently create or destroy user-facing features.

### Staged pipeline

1. **Contract and source registry.** Store source adapter config, boundary, CRS/vertical datum, licence, attribution, cadence, retention, key requirement and known limitations. Block ingestion when a source has not passed the relevant approval gate.
2. **Immutable raw snapshots.** Download or query only permitted data. Record URL, request parameters, release/version, checksum, capture/update date, terms snapshot, row/feature counts and ingestion run ID. Keep raw data outside the browser bundle.
3. **Normalize and validate.** Reproject to WGS84 for Cesium (including explicit height reference; use EPSG:4979 only when ellipsoidal heights are actually known), validate geometry, normalize names/categories, and keep source-specific attributes rather than lossy flattening.
4. **Conflate with evidence.** Join footprint↔BIN/BBL↔PLUTO, POI↔building, POI↔NTA/CD, street↔address range, and facility↔park. Every join gets method, score and source dates. Preserve competing values and explain which field is displayed.
5. **Publish search/index data.** A PostGIS-backed service is the default citywide option; use spatial indexes plus full-text/trigram name/alias/category search and H3/geohash cells for proximity. Return canonical ID, geometry centroid, category, source freshness and confidence. A local search index must not call Google for every keystroke.
6. **Publish render data.** Generate terrain tiles and theme-partitioned 3D Tiles. Start with terrain and extruded building footprints; add roof/landmark detail as separate LOD. Embed canonical ID and compact source metadata in batch/table properties so Cesium picking can resolve to the detail API. Keep transit, POI markers, parks, traffic and temporary status overlays as separate layers.
7. **Serve with freshness.** Version immutable tile manifests and use CDN/browser caching for open, versioned assets. API records expose `observed_at` and `updated_at`. Treat MTA/traffic as short-lived streams (for example 30–60 second UI refresh targets, subject to provider terms); Google content is request-time and not put in the durable feature store.
8. **Expose provenance.** The details panel must say what the feature is, which source/release supplied each important field, source capture/update date, last ingestion time, confidence/uncertainty, source link and attribution/licence. Separate “source says operating/licensed” from “source says exists.”
9. **Adapt for more cities.** Implement `CityAdapter` interfaces for boundary/CRS, source connectors, feature mappings, local IDs, conflation rules, licensing policy, tile partition, categories and search synonyms. Manhattan configuration is data, not an `if (city === 'nyc')` branch.

### 3D tiling and interaction

Cesium owns WGS84 camera/globe/terrain, visibility, LOD, 3D Tiles streaming and feature picking. Use [3D Tiles HLOD](https://cesium.com/learn/cesium-foundations/) with regional/theme partitions and geometric-error budgets: city overview loads coarse terrain/building massing; closer views request detailed roofs/hero assets; POIs and transit remain queryable overlays. Use `scene.pick`/`pickAsync` and `Cesium3DTileFeature` properties to map a picked tile feature to `feature_id`, then fetch the authoritative detail record. Reapply selection styling when tiles unload/reload, as Cesium notes that tile unload can remove feature modifications.

Do not package all Manhattan into one Blender scene or one browser asset. Use glTF/GLB for a landmark, transit vehicle, street furniture set or other reusable hero asset after a deterministic offline QA/export step. [Blender's glTF exporter](https://docs.blender.org/manual/en/5.0/addons/import_export/scene_gltf2.html) is intended for web/native transmission and can carry mesh/material/texture/custom-property data; it does not solve city streaming, source identity or geospatial conflation. [Three.js GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html) and [Raycaster](https://threejs.org/docs/pages/Raycaster.html) are suitable for a local hero/interior/custom shader component only if Cesium cannot implement the demonstrated need. A Three.js component must receive the Cesium-selected canonical feature and must not create a second world coordinate or selection authority.

Blender MCP can help author, inspect, validate and export procedural assets offline, but it is not needed to render or stream the baseline city. The existing project research records that candidate MCP servers can execute arbitrary Python in Blender. Installation, connection, server pinning, filesystem/network scope, asset provenance and review of generated scripts require approval. Until that approval, no Blender MCP is installed or used, and the civic ingestion/3D Tiles path remains the implementation baseline.

## Vertical slice and acceptance criteria

### Slice boundary and content

Use the rectangle approximately bounded by W 14th Street, W 34th Street, the Hudson River and 3rd Avenue (clip the actual source geometries to an exact WGS84 polygon, retaining a small tile buffer). It includes Flatiron, NoMad and Union Square, ordinary and high-rise building massing, the Flatiron Building/Empire State Building and LPC assets, Madison Square/Union Square parks, dense stores/restaurants, civic facilities, subway stations, bus stops, road direction/address ranges and a representative street network. It is a pipeline test, not a claim that the visual model is survey-grade. Exclude interiors, Google photorealistic mesh, live traffic and unreviewed third-party photos from the default slice.

The slice must have an ingestion accounting report: source feature count, valid/invalid geometries, dropped records with reasons, matched/unmatched source IDs, conflict counts, tile feature counts and search-index counts. “100% coverage” means every record in the selected source snapshot is accounted for; it does not mean an open source contains every real-world business or address.

### Measurable gates

| Area | Acceptance target for the slice | Evidence |
| --- | --- | --- |
| Geometry quality | At least 99% of selected building/park/road geometries pass validity checks; all invalid records are reported and excluded or repaired by a deterministic rule. | Automated validation report and sample map. |
| Identity | At least 95% of footprint records with BIN/BBL fields retain those IDs; 100% of rendered selectable features map to a platform ID and source reference. | Join report and click test fixture. |
| Source truth | 100% of detail panels show source, source URL, release/capture/update date and confidence/uncertainty for fields displayed. | UI test and screenshot/video capture. |
| Picking | 100% of a fixed 100-feature set (buildings, landmarks, parks, streets, POIs, transit) selects the intended canonical record after tile load; selection survives tile unload/reload. | Browser playtest plus automated pick assertions where possible. |
| Search | At least 95% of a fixed query set returns the intended known feature in the top five; results include category and freshness. | Versioned query fixture and API test. |
| Coverage accounting | Every selected-source record is counted as rendered, indexed, intentionally filtered or rejected with a reason; no silent drops. | Ingestion manifest. |
| Streaming | Cold first view target ≤8 s and warm first view target ≤3 s on the agreed test network/device; pan/zoom must not request a monolithic city asset. | Browser network trace and tile statistics. |
| Runtime | Target p95 frame time ≤33 ms on the agreed desktop baseline and ≤50 ms on the agreed mobile baseline while navigating the slice; set explicit device/connection baselines before sign-off. | Fixed browser performance capture. |
| Memory | No unbounded growth during a 10-minute orbit/pan loop; define a device-specific budget before release and fail if the post-GC plateau exceeds it. | Browser memory/performance capture. |
| Freshness | UI surfaces source observed/update dates; static data release is reproducible by manifest; dynamic overlays have a visible last-update time and bounded TTL. | Manifest, API response and UI test. |
| Uncertainty | No source epoch or approximate boundary is rendered as survey/current fact; known source caveats appear in detail/help text. | Content review checklist. |

The geometric error targets should be added only after a ground-truth survey/control sample is approved. Until then, report source-to-source discrepancies and authoritative metadata rather than inventing a precision claim.

## First implementation task specification (historical; completed in the delivered foundation)

The original implementation task was to implement a source registry and offline vertical-slice ingest, without adding an external runtime provider:

1. Add a versioned registry entry for NYC Building Footprints/BUILDING, MapPLUTO, LPC sites/districts, Parks Properties/Active-Passive, Facilities DB, DCP Centerline, NYC elevation metadata, MTA static GTFS and one approved Overture/OSM snapshot. Each entry must include terms URL, attribution, release/capture/update fields, cadence, retention, licence class, key/agreement requirement and `approval_status`.
2. Define TypeScript/JSON schema for `Feature`, `SourceRef`, `LicenseRef`, `IngestionRun`, `FeatureLink` and tombstone/alias records. Validate WGS84 geometry, heights/vertical datum, required provenance and source-specific IDs.
3. Download only the approved open files into an immutable raw snapshot layout; emit checksums and counts. Do not put keys in source control and do not call Google, MTA realtime, 511NY or a hosted tile service.
4. Normalize and clip the Flatiron–NoMad–Union Square polygon. Join building footprints to BIN/BBL/PLUTO where possible; attach NTA/CD, LPC, parks, facilities, transit and POI records while preserving unmatched/conflicting links.
5. Emit a small 3D Tiles tileset with extruded building massing and metadata, plus vector/JSON overlays for roads, parks, landmarks, facilities, transit and POIs. Add a Cesium pick-to-detail lookup and source-aware inspector. Keep the current generated marker as a test fixture only.
6. Add ingestion accounting, fixed 100-feature pick fixture, fixed search query fixture and the acceptance captures above. Run typecheck, lint, tests, build and browser verification on the agreed baseline.

This task should stop at the approval gates below if the selected download terms, Overture licence mix, MTA usage, tile hosting or device budget has not been accepted.

## Approval questions and blockers

The coordinator must obtain answers before integration:

1. Is legal review complete for NYC Open Data disclaimer/notification requirements and for distributing derived tiles that combine NYC, OSM/ODbL, Overture CDLA/Apache/ODbL and optional Wikimedia files?
2. Is the default open/civic + Overture/OSM stack approved, including Overture's per-source attribution/licence handling and release-file retention policy? Should ODbL sources be isolated or is a share-alike derived database acceptable?
3. Should city-scale tiles be self-hosted (requiring approved object storage/CDN/operations) or should Cesium ion be used (requiring an account, token, usage/hosting budget and terms review)?
4. Are MTA static feeds approved now, and are logos/maps/IP, GTFS-RT, Bus Time API keys and any commercial/ad-sponsored use approved?
5. Is live traffic a product promise? If yes, approve NYC DOT data-sharing/contact work and/or 511NY registration/agreement/key, plus the semantics (live versus simulated versus historical) and TTL/privacy policy.
6. Is Google Places/Routes/Map Tiles allowed as a premium request-time adapter? If yes, approve Cloud project, API keys/OAuth, billing ceilings, attribution/Google-map UI, Terms/Privacy Policy and the no-cache/non-canonical-data constraints. Google must not be scraped.
7. Is Wikimedia or another photo source approved on a file-by-file licence/attribution basis? Are photos display-only, or may approved files be included in durable assets?
8. May Blender MCP be installed/connected? If yes, approve the exact server/revision, arbitrary Python execution risk, local filesystem/network scope, credential isolation, generated-script review and offline-only role. Do not install it before this answer.
9. Are hero landmarks, interiors, custom shaders or a Three.js island in scope? If yes, define the fidelity target and asset-rights process; otherwise keep Blender/Three.js out of the baseline.
10. What device, browser, network, memory and frame-time baseline is the release gate? The performance numbers above are proposed targets, not measured results.
11. Is hosted storage, CDN, observability or a paid search/database service approved? These are architecture and cost decisions, not implementation defaults.

## Recommended default stack in one paragraph

React + TypeScript + Vite; CesiumJS as the sole world viewer; self-hosted, versioned OGC 3D Tiles and terrain; PostGIS plus full-text/trigram search; NYC civic datasets for authoritative Manhattan geometry/land use/parks/landmarks/facilities/streets/elevation; Overture/OSM snapshots for cross-city places and network enrichment with record-level licences; MTA static GTFS for transit; no live traffic, Google, hosted tile vendor, Blender MCP or Three.js in the baseline. Every feature keeps a platform ID, provider IDs, geometry/vertical reference, source/release/capture/update dates, licence/attribution and confidence/uncertainty, and every city is configured through a `CityAdapter`.
